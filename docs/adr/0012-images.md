# ADR 0012: 画像のアップロードと配信

- 日付：2026-10-15
- 状態：採用（ローカル workerd と Chromium で検証。R2 のカスタムドメインと実機の写真選択は未検証）
- 変更する設計：§10.2 の「署名付き PUT URL でブラウザから R2 に直接アップロードする」

## 決定

### アップロードは Worker を経由して非公開の pending バケットへ送る

| 段階 | 処理 |
|---|---|
| 1. 挿入 | 貼り付け、ドラッグ＆ドロップ、「画像」ボタンでエディタに入れる。クライアントで asset ID（UUID）を作り、本文に `[asset:ID]` を独立した行として挿入する。Blob は IndexedDB の `uploads` に保存し、object URL ですぐにプレビューする |
| 2. 送信 | `PUT /api/owner/v1/assets/{id}`（本人・CSRF・Origin 必須）。本文を読みながら 10MiB を超えた時点で 413 を返し（Content-Length の申告は信用しない）、PENDING の `pending/{id}` に保存する |
| 3. 確定 | `POST /api/owner/v1/assets/{id}/complete`。ファイル先頭のバイトで形式（JPEG / PNG / GIF / WebP）と縦横を判定し、4000 万画素までに制限する。SHA-256 を計算して MEDIA の `originals/{sha256}.{ext}` に不変のオブジェクトとして保存し（`cache-control: immutable`）、`assets` を `ready` にして pending を消す |
| 4. 再送 | 送信も確定も冪等。応答が失われたり、途中で切断されたり、リロードしたりしても、IndexedDB から同じ ID で再開できる |

**署名付き URL を採用しなかった理由**

- R2 の S3 API キー（secret）とバケットの CORS 設定が不要になる。
- 転送中にサイズの上限を守れる（設計 §10.2 で「保存後の検証だけでは厳密に制限できない」と指摘されていた問題がなくなる）。
- miniflare でも同じ流れで動くので、ローカルと CI でテストできる。
- 画像は 10MiB までなので、Worker を通す負荷は小さい。配信は Worker を通さない（下記）。

### 配信

- **production / staging**：`MEDIA_BASE_URL=https://media.infixer.link`（R2 のカスタムドメイン＋CDN）。アプリの Worker は画像のバイトを返さない。CSP の `img-src` には、`hooks.server.ts` がこのオリジンを追加する。
- **ローカル**：`MEDIA_BASE_URL=/media`。`/media/originals/{sha256}.{ext}` だけを Worker が MEDIA バインディングから返す（ほかの値のときは 404）。
- 本文に書くのは `[asset:ID]` だけで、ホスト名は書かない（設計 §6.1）。表示するときに URL・幅・高さに変換し、`<img width height loading="lazy">` で表示するので、レイアウトがずれない。
- サイズ別の配信（Cloudflare Images Transformations）は**有効にしていない**（課金が発生するため、有効にするときにユーザーに確認する）。今は原本をそのまま表示している。

### 公開の保留（設計 §10.2）

- 送信が終わっていない画像を参照している版は公開しない。自動保存の状態は `uploading`（「画像を送信中（端末に保存済み）」）になり、下書きは端末に残る。
- 送信に失敗した画像は「再送信」か「画像を外す」を選べる。外せば文字だけを公開できる。
- 画像を挿入した直後とページを離れるとき（pagehide）に、下書きをすぐ保存する。

### 拒否するもの

- SVG（スクリプトを含められるため）。
- HEIC / AVIF（「JPEG で書き出してください」と案内する。iPhone の写真選択で実際に何が渡されるかは実機で確認する）。
- 中身が画像でないもの、10MiB または 4000 万画素を超えるもの。

### EXIF

原本をそのまま公開する。最初に画像を挿入したときに、「原本のまま公開されます（撮影位置などの情報を含む場合があります）」と表示する。位置情報の除去は、向き（Orientation）を保ったまま処理できる仕組みを検証してから入れる。

### 重複

同じ内容の画像は同じオブジェクトを共有する（`object_key` は一意にしない。asset ID は別々）。設計 §7.1 の `assets.object_key UNIQUE` と `upload_intents` テーブルは採用しない（ID ごとに冪等な PUT / complete で足りるため）。

### リンクカードの画像（ADR 0010 の続き）

- `og:image` は、ページ本体の取得と同じ安全策（http / https のみ、プライベートアドレスの拒否、リダイレクトの再検査、5 秒）に加えて、`image/*` であること・5MiB 以下であること・中身が画像として判定できることを確かめてから、MEDIA に取り込む（`assets.source = 'link-preview'`）。
- カードは文字を左、画像を右（幅 35%）に並べる（infixer.net に合わせた）。
- 外部の画像を直接表示することはしない。

### 自分のページの OGP 画像

ページで最初に出てくる画像を `og:image` に出す。

## 未対応・後続

- pending に残ったファイルと、どこからも参照されない公開画像の削除（GC）は Phase 8 で行う（定期実行、履歴とバックアップの参照を確認してから）。
- サイズ別の配信（Transformations）、HEIC からの変換、EXIF の位置情報の除去。
- オフラインで送れなかった画像を自動で再送する仕組みは Phase 6。今は、リロードしたときか手動の再送信で再開する。
