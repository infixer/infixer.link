# ADR 0013: 日本語検索と公開表示の性能

- 日付：2026-10-16
- 状態：採用（ローカル workerd・合成データ 2,000 / 10,000 ページで検証。本番 D1 は未検証）
- 関係する設計：§4.1（検索）、§11.1（日本語検索）、§12（キャッシュと性能）、§17 Phase 5
- 変更するもの：マイグレーション 0001 の検索索引の更新方法（0005 で置き換え）、画像の CSS（Phase 4）

## 決定

### 検索の組み立て（`src/lib/server/pages/search.ts`）

| 項目 | 内容 |
|---|---|
| 入力 | NFC、空白（全角スペースを含む）を 1 つにまとめる。100 文字・5 語まで。同じ語は 1 つにする。空なら検索しない |
| 語の結合 | AND。各語はタイトルか本文のどちらかに含まれればよい |
| 3 文字以上の語 | FTS5 trigram。語は必ず `"…"`（`"` は二重化）のフレーズにするので、`OR`・`NEAR`・`*`・`:` などの検索構文は効かない |
| 1〜2 文字の語 | `LIKE '%…%' ESCAPE '\'`（`%`・`_`・`\` をエスケープ）。3 文字以上の語と混ざるときは、FTS の候補を LIKE で絞る |
| 並び順 | ①名前の完全一致（別名を含む）→ ②名前の前方一致 → ③タイトルにすべての語を含む → ④本文だけ。同じ順位では現在の名前が別名より先、その中は更新の新しい順（同時刻は id） |
| 抜粋 | 最初に見つかった語の 30 文字前から 110 文字。ハイライトは `{ text, hit }[]` で返し、画面は `<mark>` で描く（HTML を組み立てない） |
| ページング | `offset`（200 まで）と `limit`（既定 20、最大 50）。順序が決まっているので、ページ間で重複や欠落がない |
| API | `GET /api/public/v1/search?q&limit&offset`（公開、`no-cache`）。全ページが公開なので本人の確認はしない |
| 画面 | `/search?q=`。JavaScript なしでもフォームで検索できる（SSR）。JavaScript があれば入力しながら検索する（200ms の debounce、AbortController、古い応答で上書きしない、IME の変換中は検索しない）。矢印キーで結果へ移動。`noindex` |

英字の大文字・小文字は、FTS（trigram の既定）と LIKE（ASCII だけ）の両方で区別しない。全角英数と半角英数は別の文字として扱う（本文を NFKC にしていないため）。

### 検索索引の更新を全件走査にしない（マイグレーション 0005）

**問題**：0001 の trigger は `DELETE FROM pages_fts WHERE page_id = NEW.id` で古い索引を消していた。`page_id` は UNINDEXED の列なので、この文は FTS の全行を読む。10,000 ページでは **保存 1 回で 10,006 行を読んでいた**。自動保存（800ms）ごとにこれが起き、D1 の rows read（課金の単位）がページ数に比例して増える。

**決定**：ページごとに安定した整数の rowid を `pages_fts_rowids (fts_rowid INTEGER PRIMARY KEY, page_id UNIQUE)` で割り当て、FTS の行はこの rowid で入れ替える。保存 1 回の rows read は **8 行**になった（10,000 ページ）。

- `pages` の暗黙の rowid は使わない。INTEGER PRIMARY KEY のない表の rowid は VACUUM で変わりうるため。
- 0005 は既存のページに rowid を振り、FTS を作り直してから trigger を置き換える（trigger の本体は検索索引の 2 文以外は 0001 と同じ）。データのある DB に 0001〜0004 を適用したあとで 0005 を適用し、削除済みのページが索引に入らないこと・rowid が一致することを確認した。

### 名前の検索は索引を使う

最初の実装は `page_names` に `LIKE '%語%'` をかけていたため、検索のたびに名前の全行（10,000 行）を読んでいた。名前は完全一致と前方一致だけを `name_key` の範囲検索（主キーの索引）で探し、「タイトルに含む」は候補のページに対して `instr` で判定するように変えた。FTS で見つかる検索の rows read は 10,000 前後から **4〜242 行**になった。

- 代わりに、**別名の部分一致**（古い名前の途中に語がある場合）では見つからなくなった。古い名前は完全一致・前方一致でだけ見つかる。

### 公開 HTML に ETag を付けない

公開 API（`/api/public/v1/pages/{id}`）は今のまま ETag（`"{id}:{revision}"`）と `no-cache` を使う。公開ページの HTML は `no-cache` のままとし、ETag は付けない。

- HTML には応答ごとに変わる CSP の nonce が入る。304 で古い本文を使い回すと、本文の nonce と新しい応答ヘッダーの CSP が食い違う。
- ページの HTML は小さく（D1 の読み取りは 1〜5 文）、再検証で節約できるのは転送量だけ。CDN での HTML キャッシュは、設計 §12.1 のとおり全域の purge を設計するまで入れない。

### 画像

- **ページで最初の画像は `loading="eager"`・`fetchpriority="high"`**、それ以外は `lazy`。最初の画像は LCP の候補になりやすく、lazy だと読み込みの開始が遅れる。
- **CLS の修正**：Phase 4 の `.img { width: auto; height: auto }` は `width` / `height` 属性による領域の確保を打ち消していた。画像の到着を 800ms 遅らせた計測で **CLS 0.224**（予算 0.1）だった。`width: auto` を外し、`max-width: 100%`・`height: auto`・`object-fit: contain` にして **CLS 0.000** になった。縦長の画像が `max-height: 70vh` に当たる場合は、枠の中で縦横比を保って左上に寄せる（その場合、角丸は枠に付く）。

## 計測（`docs/performance.md` の Phase 5）

`pnpm --filter web perf:data`：決定的な合成データ（日記 40%・平均 650 文字・3% は 1 万文字前後・ハブとなるタグを 30% のページに付ける）を workerd のローカル D1 に入れ、各操作を 30 回計測する。検索の p95 は 10,000 ページで最大 40ms（1〜2 文字の LIKE）、FTS は 13ms 以下。予算（p95 500ms）はローカルでは満たす。

## 代案

| 代案 | 採用しなかった理由 |
|---|---|
| アプリ側の n-gram 転置索引（設計 §11.1 の 4） | trigram が動き、10,000 ページでも速度は十分。書き込みと容量が増える |
| 1〜2 文字も FTS で（unicode61 などの別の tokenizer を併用） | 日本語の 1〜2 文字は分かち書きなしでは区切れない。LIKE で 10,000 ページ p95 40ms なので不要 |
| bm25 による並び替え | 比較はしていない。日記と Wiki では、名前の一致と更新の新しさで並べる方が結果を予測しやすいと判断した。必要になったら同じ順位の中で使う |
| 検索結果をカーソルでページング | 順位付きの結果ではカーソルが複雑になる。順序が一意なので offset（上限 200）で足りる |
| `pages.rowid` を FTS の rowid に使う | VACUUM で変わりうる |
| 公開 HTML に ETag | 上記（CSP nonce） |

## 未検証・残るリスク

- **本番 D1 での挙動と時間**（staging 未作成）。ローカルの計測値は参考値。
- **1〜2 文字の検索は全ページを読む**（10,000 ページで 1 回 1〜2.4 万行）。検索は公開 API なので、繰り返し呼ばれると rows read が増える。入力中の検索は debounce と IME の変換中の停止で回数を抑えている。必要になったら Cloudflare の rate limiting ルール（Phase 8）で制限する。
- **関連ページの接続集中**：#読書 のように 3,000 ページから参照されるタグを含むページでは、関連ページの問い合わせが 1 回 約 2.8 万行を読む（時間は p95 8ms）。公開ページを開くたびに発生するので、閲覧数によっては D1 の無料枠（1 日あたりの rows read）に効いてくる。キャッシュするか、関連ページを本文の表示後に取得するか、`page_links` に更新時刻を持たせるかを、staging の実測を見て判断する。
- **補完（`/api/owner/v1/titles`）は名前の全行を読む**（Phase 3 の実装、`LIKE '%…%'`）。本人だけの機能なので今回は変えていない。
- 実機の IME での入力中検索（CDP でのエミュレーションでは、変換中に検索しないことを確認した）。
